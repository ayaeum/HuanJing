# 高并发多模态帖子与 AI 分身互动系统技术方案

版本：v1.2｜日期：2026-10-28｜状态：已完成两轮交叉与对抗性设计审查，尚未实施或压测

## 1. 设计结论与范围

采用 Go 服务、Temporal 持久工作流、PostgreSQL 业务账本、Qdrant 向量检索、MQ 事件分发及对象存储。

**方案概括：**系统预先根据获授权的分身人设、兴趣和公开经历，建立可检索画像。用户发帖后，先完成多模态审核与理解，提取主题和互动诉求，再通过语义、关键词、关系及有限探索多路召回分身，经资格过滤、去重和重排，筛选少量候选。随后，每个候选结合自己的人设及授权记忆，决定忽略、点赞、评论或两者兼有。整条链路由持久工作流推进，阶段结果和动作回执均持久化。系统通过按动作幂等、版本与权限校验、有限重试和全局配额，应对重复任务、依赖异常和服务重启。

用户发布文本、图片、音频或视频帖子后，系统异步完成媒体处理、审核、语义理解、分身召回、个性化决策和互动发布。分身根据人设及获授权的历史记忆选择忽略、仅点赞、仅评论或点赞并评论。处理结果可查询，技术失败与业务忽略分别展示。

本系统 PostgreSQL 为互动发布的权威库，决定互动是否存在及是否可见。Temporal 推进执行，MQ 分发事件，Qdrant 提供候选，三者均不承担最终授权裁决。

本次设计覆盖完整业务链路、重复任务处理、服务重启恢复、外部调用异常、并发删除撤权、索引一致性、模型版本管理、容量控制、可观测性和故障验收。模型训练、底层集群搭建、无限制自主 Agent 工具调用不在本次范围内。

### 1.1 固定的业务语义

1. 用户提交成功表示帖子版本与处理任务已持久化；审核通过后才对自动互动链路开放。作者可以查看待审内容。

1. 每个租户内，同一帖子、同一分身只有一个最终决策槽，保存 planned\_actions 动作集合：空集表示 IGNORE，\[LIKE\] 表示仅点赞，\[COMMENT\] 表示仅评论，\[LIKE, COMMENT\] 表示点赞并评论。点赞与评论可以同时执行，各动作分别幂等；同一自动互动周期内最多一次点赞和一条评论。

1. 内容编辑生成新版本；尚未最终提交的提案可以重算，已最终提交的决策保持稳定。已发布评论不会因编辑自动追加第二条。删除、撤回和再次互动属于独立显式命令。

1. 互动按候选独立完成，某个分身失败不回滚其他成功互动。整帖以完成、部分完成、失败等状态收敛。

1. 删除使帖子及其互动在权威读取路径立即不可见。已发送到设备的通知无法保证撤回；通知展示必须重新检查资源可见性。

1. 全局召回只使用允许用于发现的人设与兴趣信息。私有记忆仅在该分身授权范围内用于判断，公开评论采用单独的公开上下文。

### 1.2 必须守住的不变量

| 编号 | 不变量 | 实现边界 |
| --- | --- | --- |
| I1 | 接收成功的任务有持久记录和明确结局 | 帖子、job、启动 outbox 同事务 |
| I2 | 每个帖子与分身最多一个最终决策 | 数据库唯一槽位与幂等提交 |
| I3 | 未通过审核、已删除、无权限或过期的提案无法新发布 | 最终提交事务与权限 guard |
| I4 | 旧执行者和旧帖子版本无法覆盖新结果 | recovery epoch、generation 和版本比较 |
| I5 | 技术失败不会伪装为 IGNORE 或审核拒绝 | 状态机与错误分类 |
| I6 | 调用次数、候选数量、积压和预算有界 | 准入、配额、截止时间、有限重试 |
| I7 | 私有记忆不能成为公开生成输入 | 服务权限、类型化上下文和数据血缘 |

“可恢复”建立在已确认写入的数据库与工作流持久性契约之上。机房级数据丢失的 RPO/RTO 取决于现有集群配置，需在上线前验证；本文不假定跨地域异步复制具有零数据丢失能力。

Temporal 是在线处理阶段的唯一重试编排者。MQ 消费失败只重试事件落地；模型任务重投与同一 Activity 的自动重试必须避免同时发生。Outbox dispatcher 只保证事件或工作流启动被可靠交付。

Go 负责 API、工作流和业务服务；模型调用通过接口适配。需本地推理或特殊媒体库时可用独立 Python Worker，通过稳定 schema 接入，避免跨语言实现共享可变状态。

## 3. 端到端流程

### 3.1 接收与工作流启动

客户端先上传媒体，获得归属已验证的对象引用。Post API 校验文本和媒体限制、幂等键及租户配额，同事务写 post、post\_revision、processing\_job 和 outbox，再返回 HTTP 202、post\_id、version、job\_id 与状态查询地址。

客户端重复请求使用唯一键 `(tenant_id, author_id, idempotency_key)`；相同输入摘要返回原 job，不同摘要返回冲突。幂等键保留到约定重试窗口结束，之后请求必须明确作为新提交。媒体引用须验证归属，禁止凭任意 URL 让服务抓取内网资源。

### 3.2 多模态解析、审核与理解

基础检查先验证真实 MIME、大小、时长、像素、压缩展开上限和解码 CPU/内存预算；媒体在隔离 Worker 中处理。原始内容按版本和 content\_hash 不可变存储，派生产物记录来源和转换器版本。

图片产生视觉描述与 OCR；音频产生 ASR、语言、时间戳；视频生成带时间轴的片段证据、音轨转写及场景信息。它们用于语义理解和辅助审核，不能用几个抽样帧宣称整段视频已审核。

审核适配器返回 `PASS / REJECT / REVIEW_REQUIRED`，附策略版本、媒体覆盖区间、缺失模态和原因码。供应商超时、文件未完整处理、覆盖不足均不会进入 PASS；后者可进入人工复核。需要人工处理的任务有明确截止时间，过期后不继续生成过时互动。

通过审核后，理解服务生成结构化内容：主题、实体、情绪、语言、可互动点、证据片段和时间戳、不确定性标记，以及 model/prompt/schema 版本。无法确定的事实保持未知，避免把推测写成帖子事实。

多模态理解结果可与审核并行计算以降低延迟，但只有审核通过的产物能进入召回；是否提前消耗理解额度由成本策略决定。所有成功结果先持久化，Activity 返回引用。

### 3.3 召回、重排与候选冻结

召回要回答的是“哪些分身值得进一步判断这条帖子”，而最终决策回答“这个分身现在是否愿意点赞或评论”。系统先用可索引的画像缩小范围，再让少量候选结合自己的授权记忆判断意愿，避免对全站分身逐个调用大模型。候选生成、评分、重排采用分阶段结构。\[S1\]

#### 3.3.1 分身如何成为可检索对象

分身创建、人设修改或获授权的公开兴趣变化后，异步生成发现画像。画像包含稳定人设、擅长领域、兴趣主题、语言，以及允许用于匹配的近期公开兴趣；职业、兴趣和经历必须有用户配置或授权来源，不能把模型猜测当成事实。

一个分身可以有多个画像片段，例如“长期跑步”“户外摄影”“擅长器材建议”，分别生成向量，避免将多个兴趣压进一个长摘要后相互稀释。公开索引每个点保存 avatar\_id、profile\_type、source\_revision、chunk\_id、embedding\_version 和必要过滤字段，完整身份及乱序处理遵循第 7 节。

私有聊天、私密经历和未获授权的记忆不进入公开发现索引，也不能先由模型概括成兴趣再绕过公开权限。用户可以明确授权哪些资料用于发现。画像更新通过 outbox 进入索引；没有历史的新分身可以仅依靠主动填写的人设和兴趣进入召回。

#### 3.3.2 帖子如何生成召回查询

审核通过后，从多模态理解结果提取主题、实体、公开事实和互动诉求。例如，“分享一次登山经历”与“询问新手登山装备”的主题相同，但适合的分身侧重点不同。查询同时表达帖子讲什么、希望获得哪种互动，并保留来源证据。

每帖生成数量有上限的查询表示，例如一个内容摘要向量、一个互动诉求向量，加上关键词和主题标签。查询编码器与画像编码器必须来自兼容的同一 search\_bundle。图像内容可先转为带证据的文本语义；确有必要时增加独立视觉召回通道，再融合候选排名，不直接混加不同向量空间的分数。

帖子查询只需计算一次即可检索大量预计算画像。人设变更才更新对应索引，不在每次发帖时重新向量化全部分身。

#### 3.3.3 多路召回怎样找到候选分身

先确定租户、发现授权、分身有效状态、可见范围和语言等资格约束。索引可表达的条件在检索时前置过滤；实时屏蔽关系、当前权限和版本在候选返回后由权威库批量核验。所有通道都执行同一资格规则，关系或探索通道不能绕过过滤。\[S2\]

并行运行四路召回，各路有独立预算：

- 语义兴趣路：用帖子摘要和互动诉求向量搜索分身画像，找主题相关或擅长回答该问题的分身。

- 关键词与主题路：用主题、实体、术语及稀疏文本检索补充精确匹配，减少型号、地名和专业词被纯向量召回遗漏的情况。

- 关系路：从允许使用的关注、历史公开互动等关系中提取候选，再按本帖相关性筛选；关系近不意味着每帖都必须互动。

- 探索路：为新分身和长尾兴趣保留少量候选机会。先满足主题相关性底线，再在合格集合内抽样；固定抽样种子并保存结果，限制探索比例。

各路返回的片段先批量通过权威版本与资格核验，再按 avatar\_id 聚合。旧版本高分片段不参与排名。每个查询对一个分身只取其最佳有效片段的匹配分数，再生成分身级排名；同一路包含摘要、诉求等多个查询时，以固定权重合并这些排名，不按命中片段数量累加。分数相同时，按稳定的 avatar\_id 次序排序。同一分身只占一个候选位置，并限制证据片段数。分路检索适度 overfetch 后再聚合，避免多画像分身挤满 TopK；补取次数和扫描量均有限。

#### 3.3.4 候选如何合并、重排和缩小

各路分数尺度不同，先将每一路转成分身级排名，再用加权 RRF 等按名次融合的方法合并，避免直接相加 cosine 相似度、关键词分数和关系分数。一个可实现的融合式为：fusion(a)=Σ w\_r/(k+rank\_r(a))；未命中的通道不贡献分数，w\_r 和平滑常数 k 经评测确定。Qdrant 提供混合及多阶段查询和 RRF 能力；跨关系通道的分身级融合在匹配服务中完成。[Qdrant 混合检索](https://qdrant.tech/documentation/search/hybrid-queries/)

合并去重后保留至多 K 个候选，权威库批量核验资格、画像版本和屏蔽关系。随后用轻量重排器评价“帖子内容与诉求—分身公开画像”的匹配度，结合授权关系、近期互动次数、活跃度和当前互动预算排序。首版使用可解释、经过校准的特征规则或轻量 reranker；积累人工标注和真实反馈后再引入学习排序，避免直接用模型自评分当成可靠概率。

最后执行多样性和频控重排，限制相似人设集中、同一分身反复出现以及热门分身被过度消费，选出最多 N 个候选进入个性化阶段。低于质量阈值时允许不足 N 个，也允许零候选；资格过滤与质量门槛不为凑数放宽。

参数示例仅用于理解链路：语义路取 100 个分身、关键词路 50 个、关系路 30 个、探索路 10 个，去重及资格检查后重排，最终选择最多 10 个分身进行决策。实际每路预算、K、N、评论上限 M 和执行并发 W 由效果、供应商额度与压测确定；本例不代表容量承诺。

#### 3.3.5 人设和历史记忆在哪一步发挥作用

初筛只使用获授权的发现画像。进入 N 个候选后，才按每个 avatar\_id 在自己的授权范围检索与本帖相关的记忆，并结合人设、关系及近期行为生成 planned\_actions：忽略、仅点赞、仅评论或点赞并评论。被召回只表示有潜在相关性，最终可以选择忽略。

私有记忆可以影响内部动作判断，但公开评论仍使用第 3.4 节规定的隔离上下文。共同决策来源与动作专属来源随提案保存。最终发布时，继续校验版本和授权。因此，“匹配到某个分身”不会自动获得读取其全部记忆或公开其经历的权限。

例：用户发布“第一次跑半马，最后五公里很吃力，附运动截图”。系统识别半马、配速和体能管理，并区分分享与求助。语义路找到跑步爱好者和耐力训练方向分身，关键词路补充半马经验，关系路补充近期有相关公开互动的分身。重排后只有少量候选进入记忆判断：有相关公开经验的分身可以点赞并给出个性化评论；预算用尽或不愿重复发言的分身可以忽略。截图中无关的隐私字段不作为发现特征。

#### 3.3.6 冻结、恢复和效果验证

保存不可变 candidate\_snapshot：帖子及查询版本、search\_bundle、各路分身级名次与命中证据、资格版本、重排策略、探索种子、最终名单及过滤原因。阶段重试复用该名单，避免同一次任务不断换分身；授权和内容版本仍在动作提交时重新检查。

候选不足时做有界补召回；服务超时与索引明显滞后按第 5 节记录等待、失败或 RETRIEVAL\_DEGRADED，不能伪装成正常零候选。缓存键包含帖子、bundle 和资格版本，缓存结果也必须通过当前权威资格检查。

检索近似误差与业务相关性分别评估。在可控数据集上，固定相同 tenant、ACL、来源版本、query bundle、分身聚合规则和目标 K，构造精确的分身级 TopK 基线。用该基线评估 ANN 分身级 Recall@K，同时报告 ANN 的扫描预算、延迟和过滤后候选数量。禁止把片段级 ANN 与无过滤的精确结果混比。另用人工标注的“帖子—分身”相关性集合独立衡量业务 Recall@K、重排质量、多样性及冷启动覆盖，区分近似检索损失与画像本身的语义质量。线上同时看有效互动率、忽略率、负反馈、重复度和成本；不单独优化评论数量。按主题、语言和新老分身分层观测，避免整体指标掩盖长尾质量。

### 3.4 分身决策与公开评论

每个候选读取版本化人设，并在该分身范围内检索授权历史记忆。决策模型输出经过 schema 校验的 planned\_actions 集合、原因码和信心分数；集合只允许 LIKE、COMMENT 且去重，空集才表示 IGNORE。它只能提出动作，业务服务分别决定各动作能否执行。用户文本、OCR、ASR 和记忆均视为不可信数据，不能改变工具权限或系统策略。

个性化决策可以使用私密记忆，但公开评论采用第二个隔离调用，只输入帖子公开内容、公开人设、明确允许公开的记忆及已选择的动作。禁止把私有推理文本、自由文本 rationale 或未经批准的摘要复制到评论 prompt；公开上下文使用 allowlist 字段和来源标签构建。

评论生成后执行内容安全、隐私泄露、事实依据、长度和重复度检查。允许有限次数改写；仍不通过则将 COMMENT 记录为 OUTPUT\_REJECTED。若 planned\_actions 同时包含 LIKE，点赞仍可独立校验和提交；评论失败不会自动添加原计划没有的点赞，也不能把非空动作集全部失败写成 IGNORE。计划冻结后保持稳定，分别保存动作执行结果。

## 4. 持久工作流设计

主流程 PostProcessingWorkflow(job\_id, recovery\_epoch)：检查任务 → 解析与审核 → 理解 → 召回快照 → 有界候选流程 → 汇总。候选流程 AvatarDecisionWorkflow：读取人设和记忆 → 冻结动作计划 → 分别推进点赞、评论生成与审核 → 按动作提交并汇总。LIKE 可以先完成，COMMENT 单独重试或失败；计划冻结不等于动作执行完成。

媒体子任务按文件和分段设置上限，候选子流程按窗口 W 启动；上一批完成后推进下一批，避免一次创建无界子流程。复杂长视频分批持久化进度；主流程只持有引用和计数。到截止时间时停止发起新调用，取消未完成候选并等待其状态收敛；数据库提交栅栏负责阻止迟到结果。

工作流代码保持确定性：系统时间、随机数、外部查询和模型调用通过 Temporal 支持的机制或 Activity 获取。已记录的完成结果在 replay 中复用；远端已执行而结果尚未记录的 Activity 仍可能重试，因此业务幂等必需。\[S3\]

Task Queue 按阶段和供应商隔离，例如 media、moderation、embedding、decision、generation、commit；Worker 并发只控制本地资源，供应商全局 RPM/TPM 和并发由网关控制。下游缺额时返回 retry\_after，由工作流持久定时等待，避免长期占用线程和连接。

### 4.1 身份与版本

| 标识 | 定义 | 用途 |
| --- | --- | --- |
| post\_id / content\_version | 帖子身份与单调递增内容版本 | 防旧内容发布 |
| job\_id | 唯一 tenant + post + version + pipeline\_revision + execution\_mode | 长期业务任务去重和影子隔离 |
| recovery\_epoch | 受控恢复代次 | 拒绝旧执行者提交 |
| workflow\_id / run\_id | post/job/epoch；run 为运行记录 | 编排追踪，不作互动幂等键 |
| stage\_key | 不可变阶段绑定输入摘要；候选阶段另绑定 proposal\_generation 与 input\_snapshot\_hash | 精确复用同输入的成功阶段 |
| operation\_key | 阶段操作身份，绑定规范化输入摘要 | 供应商幂等及调用账本 |
| decision\_slot | 唯一 tenant + post + avatar | 单个最终决策 |
| proposal\_generation | 未提交提案的计算代次 | 编辑、恢复、重算栅栏 |

模型、prompt、schema、审核策略、embedding 和排序配置各自版本化；尝试次数只属于执行记录。Continue-As-New 不改变 job、stage 和 operation 身份。人工重新分析使用新 pipeline\_revision，但仍经过同一决策槽，无法追加重复互动。

帖子解析等不可变阶段的 stage\_key 包含 job、stage、媒体 item、内容摘要和处理配置版本。候选的记忆、决策、生成阶段进一步包含持久化 proposal\_generation 与 input\_snapshot\_hash。普通重试和 Continue-As-New 沿用身份；记忆撤回、输入变化后的合法重算，在事务内推进槽位 generation 并生成新输入快照，创建新的 stage/operation 身份。新提案只引用该 generation 和输入快照的结果，旧 SUCCEEDED 不能跨输入复用。

同帖子版本的人工重算必须通过控制接口设置 active\_pipeline\_revision，并推进未提交槽的 generation；自动重放旧事件没有提升版本的权限。最终提交校验当前 active\_pipeline\_revision，防止新旧 job 并发时旧策略抢先发布。编辑或多次重算达到单帖重算上限后停止，避免持续变化引发无限生成。

### 4.2 启动丢失与受控恢复

Dispatcher 用固定 workflow\_id 启动，同 ID 已存在时必须核对 job 和输入摘要；历史保留期内拒绝任意复用已关闭 ID。PG job 账本承担跨历史保留期的长期去重。

Reconciler 扫描未启动、长期无进展、编排已关闭但业务未收敛的任务。查询 Temporal 失败时按依赖故障处理，不能因为网络异常创建新工作流。受控恢复需要确认旧编排已终止或关闭，CAS 增加 recovery\_epoch，并在新执行中复用可验证的已提交阶段结果。

旧 Activity 可能在工作流终止后仍返回，因此阶段提交、提案更新和最终发布都要检查当前 epoch/generation，并持 processing\_job 共享锁到事务结束。恢复升 epoch、取消与终态更新持冲突写锁；所有更新带允许前态和当前 epoch 条件，避免主流程汇总覆盖 CANCELLED/SUPERSEDED。恢复之前已提交的业务结果保留，恢复线性化之后旧 epoch 无法新提交。恢复工具必须展示原任务、恢复原因、可重用阶段和预计副作用，记录操作者与审计原因。

## 5. 数据模型与状态机

所有业务唯一键均包含 tenant\_id。以下是逻辑模型，实施时补齐外键、索引、归档和数据库迁移，不将本表直接当作已执行 DDL。

| 表 | 关键字段和约束 | 作用 |
| --- | --- | --- |
| post / post\_revision | current\_version、deleted\_at、acl\_epoch；版本内容不可变 | 帖子权威状态及历史 |
| processing\_job | job\_id、execution\_mode、deadline、pipeline\_revision、recovery\_epoch、status | 任务账本与聚合进度 |
| stage\_result | 唯一 stage\_key、input\_hash、generation、result\_ref、status | 阶段恢复及成功结果 |
| candidate\_snapshot | job\_id、search\_bundle、候选版本与分数、快照 hash | 固定召回结果 |
| decision\_slot / proposal / action\_execution | 槽唯一 post+avatar；planned\_actions、generation、输入版本；动作记录唯一 decision+action\_type | 冻结计划、提案及逐动作状态 |
| interaction | 唯一 decision\_id+action\_type、内容引用、visibility、source\_revision | 权威互动实体 |
| external\_operation / attempt | 唯一 operation\_key；attempt、charge\_identity、provider\_id、result\_ref、cost | 逻辑操作、计费单元及未知结果 |
| outbox / consumer\_inbox | event\_id、aggregate\_version、destination；consumer+event 唯一 | 可靠事件交付 |

补充表：authorization\_guard（固定存在的授权行与 epoch）、quota\_bucket / reservation（原子预算预留）、memory\_source（来源、公开级别、删除墓碑）、index\_projection（预期版本与索引进度）。运行日志只作诊断，不能替代这些账本。

### 5.1 整帖任务状态

`ACCEPTED → PROCESSING → COMPLETED / PARTIAL_COMPLETED`。审核需要复核进入 `REVIEW_REQUIRED`；依赖等待进入 `WAITING_DEPENDENCY`；不可确定外部写入进入 `NEEDS_RECONCILIATION`。

终止状态包括 REJECTED、SUPERSEDED、CANCELLED、EXPIRED、FAILED。COMPLETED 表示候选全部选择空计划（业务忽略）或其所选动作全部成功；仅冻结计划不算执行完成。只有检索成功且达到约定索引 freshness 要求时，零候选才可用 NO\_ELIGIBLE\_CANDIDATE 原因码；它表示本次检索及过滤没有合格结果，不证明近似检索覆盖了全库。PARTIAL\_COMPLETED 表示候选间或同一候选的动作间出现部分成功、部分技术失败或输出被拒。FAILED 表示无有效候选结果且处理失败。已知全部失败、过期或取消的原因均持久化，不依赖工作流 UI 推断。

Qdrant 超时或服务不可用进入 WAITING\_DEPENDENCY，耗尽预算后 FAILED/EXPIRED；不能转成零候选成功。索引落后但业务允许继续处理部分有效结果时，记录 RETRIEVAL\_DEGRADED、实际水位、缺失范围和候选数，整帖汇总至 PARTIAL\_COMPLETED；没有可用结果且无法判断缺口时等待或失败。

主流程按候选终态汇总；存在未解决的外部发布 UNKNOWN 时保持 NEEDS\_RECONCILIATION，不能显示完全完成。截止时间后技术待办可过期，但外部 UNKNOWN 仍保留对账状态。

### 5.2 阶段和提案状态

阶段：`PENDING → RUNNING → SUCCEEDED`，异常为 RETRY\_WAIT、FAILED、UNKNOWN、CANCELLED。迟到错误不能覆盖成功结果。

计划：PROPOSED → READY → COMMITTED；COMMITTED 仅表示 planned\_actions 已冻结，不能解释为所有动作已完成。冻结空集代表 IGNORE，不创建互动。每个非空动作分别保存 PENDING、READY、SUCCEEDED、OUTPUT\_REJECTED、FAILED、UNKNOWN、EXPIRED 或 STALE。候选执行结果另行汇总。全部成功为 COMPLETED，部分成功为 PARTIAL\_COMPLETED。存在 UNKNOWN 时为 NEEDS\_RECONCILIATION，已成功动作保持成功。非空计划全部失败属于失败。共同决策材料失效时，影响全部未完成动作；评论专属材料失效时，只影响 COMMENT。

帖子编辑使旧 job 标记 SUPERSEDED，并提高未提交槽的 generation 或使其输入版本失效；新 job 可在同一槽上产生新提案。已冻结槽返回原计划，继续推进其中尚未完成且仍符合当前版本和授权的动作，禁止因计划已冻结而跳过未决评论。旧内容版本尚未外发的动作标记 STALE，已成功动作保持稳定。已外发但结果 UNKNOWN 的动作继续对账；确认未生效后才可标记 STALE，确认已生效则按撤回治理处理。实现区分占位、计划冻结和逐动作完成，冻结前合法重算可以更新提案；冻结后重试只能恢复原计划内的动作。

## 6. 外部调用、超时和预算协议

网关创建 external\_operation，固定输入摘要、模型版本、供应商和预算策略。同 operation\_key 输入不一致立即冲突；SUCCEEDED 返回原引用，RUNNING 按当前尝试查询或等待，不能盲目并发创建第二次调用。

网络尝试前持久化 attempt 和预算预留。每个可能独立收费的 attempt 有独立 charge\_identity，并在发送前原子预留最坏允许费用；旧 UNKNOWN 预留保持占用。只有供应商明确保证同一幂等请求不会重复收费，多个网络尝试才能共享计费身份。供应商支持幂等键时，复用逻辑 operation\_key；支持异步查询时，保存 provider\_job\_id。收到回调后，执行验签、事件去重和状态条件更新。回调先持久化结果再通知工作流，即使通知丢失也可由查询恢复。

| 情况 | 处理 | 最终语义 |
| --- | --- | --- |
| 429、暂时性网络故障、可恢复 5xx | 指数退避、抖动、尊重 Retry-After | 受总截止时间与预算约束 |
| 输入错误、鉴权错误、无效模型配置 | 停止自动重试并告警 | FAILED，修正后受控恢复 |
| 审核明确违规 | 业务终止 | REJECTED |
| 远端可能执行但无回执 | 查幂等结果或异步任务；无能力则 UNKNOWN | 不假定未执行或未计费 |
| 模型生成 UNKNOWN | 在批准的调用预算内允许替代尝试 | 可能重复计费，只有一个权威结果 |
| 外部互动写入 UNKNOWN | 保持发布意图，查询对账 | 无幂等/查询能力时人工处置 |

每次替代尝试提升 attempt generation。旧尝试迟到时，可以记录费用和审计，但不能覆盖已胜出的结果。网关记录的“允许再生成”与工作流重试共用一个总尝试上限，避免多层重试乘法放大。

Temporal 配置单次 Start-To-Close、总 Schedule-To-Close 以及适用的 heartbeat timeout，含义分别是一次尝试、整个 Activity 和心跳进展边界。\[S4\] 精确数值来自供应商延迟实测；同步 HTTP 超时应短于 Activity 单次超时，长视频改为提交任务、持久等待、回调或轮询，避免长连接等待。

业务截止时间覆盖排队、重试和人工等待；到期不再发起新生成。Activity 超时不代表供应商停止运行，不能立刻回收所有远端并发占用及费用预留。存在 request\_id 时对账释放；缺少查询能力时按已知供应商最长执行期和最坏费用结算，保留未决项并限制其数量。无可靠远端终止边界时，明确只能限制本系统发起速率和未决预算，不能保证远端真实并发绝对不超限。

网关熔断按供应商与模型隔离，恢复时小流量探测，逐步放量。降级模型需通过效果及审核等价性验证，使用新 operation 身份并记录版本；不得在同一 operation\_key 下静默更换模型参数。

## 7. 向量检索与记忆一致性

### 7.1 索引组织与语义空间

`avatar_public_vX` 存允许用于发现的人设、兴趣、语言和少量公开事实；`avatar_memory_vX` 存分身记忆向量及最小必要元数据，服务凭证与公开检索分开。原始私密文本保存在受控存储，只有记忆服务可取。

公开候选查询按 tenant 和资格过滤，私有查询强制附加 tenant、avatar\_id 与授权范围；这些条件由服务端注入，调用方及模型不能删除。检索返回后批量查 PG 的来源版本、墓碑和权限，再读取原文，Qdrant payload 不能自证授权正确。

文本与多模态摘要可以进入同一文本 embedding 空间；图像向量作为独立召回通道再按排序结果融合。不同模型即使维度相同也不能直接比较或相加。search\_bundle 原子绑定 query model、维度、归一化/距离函数、chunker、collection 和融合策略。

### 7.2 索引延迟、乱序与删除

数据库事务提交来源和 outbox，索引消费者以 `(tenant_id, entity_type, entity_id, source_revision, embedding_version, chunker_version, chunk_id)` 生成不可变 point ID，旧写入无法覆盖新向量，不同 chunk 也不会相互覆盖。每个来源版本有 projection manifest，记录预期 chunk 集合、hash、完成状态和 bundle；只有全部分块完成且来源仍有效，才推进该来源版本的索引完成水位。PG 保存预期版本；旧版本返回后被过滤，后台回收旧点。允许暂时漏召回，不允许把过期资格当成可发布授权。

删除先写权威墓碑，再异步清理向量、缓存、派生文本与对象。索引落后时，检索仍由墓碑拦截。墓碑保留覆盖最大事件重放和备份恢复窗口，清理作业可对账重跑，防止迟到 upsert 让已删除记忆复活。

模型或 embedding 迁移使用蓝绿 collection、增量双写和按来源版本回填。验收覆盖率、过滤后的召回率、权限负例、延迟和更新水位后，原子切换整个 search\_bundle；请求固定 bundle 到结束。旧模型与索引保留到存量任务排空和回滚窗口结束。Qdrant 官方提供新 collection 与 alias 切换流程，本方案额外将查询编码器一起绑定切换。\[S5\]

### 7.3 记忆生成与撤回

仅已提交互动的事件可以形成“已互动”事实记忆；消费者按 `(source_interaction_id, memory_type)` 去重。使用来源互动及帖子版本作为血缘，避免把失败或 UNKNOWN 写成已发生事实。派生记忆最终落库事务与来源删除/撤回共享来源 guard：验证帖子及互动仍存在、可见、未撤回，来源版本和 source\_epoch 匹配后才创建记忆。即使摘要模型在事务外已完成，提交时也必须重验。删除先推进来源墓碑和 epoch，迟到事件因来源无效被消费为 SKIPPED\_SOURCE\_REVOKED，不能创建新记忆。

读取派生记忆时沿血缘验证来源帖子和互动的当前有效性；除自身 tombstone 外还检查来源 tombstone。清理在写入前发生也不会漏掉未来派生对象。跨库记忆投影先在权威来源库完成带 source\_epoch 的派生意图提交，外部索引只作投影，读取仍回到来源权威校验。

私密记忆只影响内部动作判断；公开评论构造器只读取 disclosure=public 且当前仍有效的事实。生成结果本身也可能推测私人信息，仍需输出审核和泄露评测，不能把上下文隔离描述为对所有语义泄露的数学保证。

记忆撤回时立即更新权威墓碑和 memory\_epoch。发布提案记录参与决策和公开生成的来源 ID、版本及记忆 epoch；同时将血缘展开为完整的 source\_guard\_id/epoch 集合，覆盖来源帖子、互动及其他可撤回实体。最终提交锁定并检查这组来源，不能只依赖异步更新的分身 memory\_epoch。发生撤回时，冻结前的提案标记 STALE 并重算。对于已冻结计划，受影响且尚未外发的动作标记 STALE。已外发且结果 UNKNOWN 的动作保留对账状态：确认未生效后才可 STALE，确认已生效则按撤回治理处理。禁止借重试新增动作。每动作记录共同决策来源与其专属材料来源的并集，评论专属材料失效不连带取消合法点赞。

每个提案限制记忆条数、血缘深度和去重后来源 guard 数量。构造输入前按相关性选取能在预算内保留完整血缘的材料；来源闭包超限或无法解析时，缩减输入或拒绝提案。来源检查必须完整保留。例：帖子 A 的评论引用源自帖子 B 的记忆，即使 B 的删除尚未传播到分身索引，最终事务也会因锁验 B 的 source\_epoch 而拒绝旧提案。

来源在最终发布之前撤回，旧提案不能发布；来源在发布之后撤回，已有互动的保留或撤回按单独的内容治理策略执行并记录血缘处置事件。该边界不承诺抹除已展示内容，也不把异步清理当作发布前授权保证。

## 8. 高并发、背压与公平性

### 8.1 容量模型

令 λ 为准入帖子数/秒，p 为审核通过率，N 为进入决策的平均候选数，c 为选择评论的比例；阶段 i 的放大系数为 a\_i，含失败的平均尝试数为 r\_i，平均调用时长为 E\[S\_i\]。

- 决策调用率：`R_decision = λ × p × N × r_decision`。

- 评论调用率：`R_comment = λ × p × N × c × r_comment`。

- 平均在途调用：`C_i ≈ R_i × E[S_i]`；该公式用于稳定区间的均值估算，P95/P99 需压测。

- 同供应商同时满足请求、token 和并发约束：`ΣR_i ≤ RPM/60`，`ΣR_i × E[tokens_i] ≤ TPM/60`。

- 积压清空时间近似 `B / (μ - λ_in)`，仅服务能力 μ 大于同单位的到达率 λ\_in 时成立。

视频按总分钟数、帧量、分辨率和转码成本单独测算；不能用平均帖子掩盖超长媒体。向量查询包含公开召回和每候选记忆检索；索引容量取决于分身数量、记忆条数、chunk 数、维度及副本，迁移需预留双索引与回填计算额度。

所有吞吐数字均为上线前压测输入，本文不承诺未经验证的 QPS。压测报告必须分别给出入口受理能力、稳定完成吞吐、模型配额上限、积压恢复速度和单位有效互动成本。

### 8.2 配额与过载策略

入口限制作者发帖频率、媒体大小、租户待处理数量和最大队列年龄。超限时返回清晰的 429/503 和重试提示；已接收任务保持可查询，最终明确过期或失败。

工作流在每帖 N 和窗口 W 内推进，网关在供应商、模型、租户和全局维度发放调用额度。网关维护持久的 permit\_waiter，唯一键为 operation\_key 与 attempt/charge\_identity，携带 tenant、预估 token、deadline；重复请求查询同一条等待记录。调度按租户使用加权 deficit round-robin，并按预估 token/计算成本扣减份额。根据等待年龄有界提升优先级，限额内可借用空闲份额。仅有集中 token bucket 和随机重试不能保证公平。

发放 permit、预留费用和标记唯一 dispatch attempt 在网关权威账本中原子完成；实际发送前再次校验 permit 有效期、任务 deadline 和当前 RPM/TPM 窗口，避免已获许可积存后集中发出。permit 到期仅在确认未发起请求时释放，已发送或 UNKNOWN 按第 6 节对账。工作流通过持久定时查询或可靠信号获知 permit，普通失败重试仍由 Temporal 负责；网关调度器只授予调用许可，不重复执行整个业务阶段。各预算域采用固定锁序或预分配有界额度，防止跨节点竞争突破硬限额。每个分身设置冷却时间和互动日额度，每帖设置评论上限 M。

流量额度可以使用集中限流服务。硬费用预算与最终互动额度由权威账本管理。限流依赖不可用时停止发起新调用或使用预先分配且有界的租户额度，禁止无限 fail-open。调用预算 reservation 通过唯一 charge\_identity 去重；确定未计费的失败可释放，未知调用保留或保守结算。相同 operation 的替代调用若可能再次计费，必须再预留，余额不足则等待或终止替代尝试。

过载优先减少探索召回和进入推理的候选数，延后非紧急互动，最后准入限流。审核能力缺失时保持待审；检索能力不足时等待、明确失败或按第 5 节记录降级，禁止全量分身扇出。自动评论使用独立容量池，防止媒体解码或大租户占满文本链路。

## 9. 最终提交事务与并发正确性

内部接口分为 FreezeDecisionPlan 与 CommitAction。FreezeDecisionPlan 在同一锁与版本校验协议下冻结 planned\_actions；CommitAction(tenant\_id, job\_id, recovery\_epoch, post\_version, avatar\_id, proposal\_id, proposal\_generation, action\_type) 只能提交冻结集合中已就绪的动作，引用其已持久化输入及审核结果。禁止客户端携带未经校验的正文或追加计划外动作；空计划可直接完成为 IGNORE。

### 9.1 同一权威事务内的处理

1. 按统一顺序获取固定存在的 guard：租户安全策略 → 分身授权与记忆 → 目标帖子和当前动作完整来源 guard 集合（共同决策来源加该动作专属来源，统一按 entity\_type、entity\_id 排序）→ processing\_job → 决策槽 → 按 key 排序的配额桶；只需部分行的事务保持相同相对顺序。发布对前四类持共享锁到提交，修改、撤权、来源删除、恢复升 epoch 和取消持冲突写锁。关系屏蔽通过固定授权 guard 的 epoch 表达，避免锁一个不存在的关系行。

1. 锁决策槽和当前 action\_execution；计划必须已冻结且包含该动作。当前动作已 SUCCEEDED 则返回原互动和回执；其他动作成功不妨碍推进当前动作。UNKNOWN 按对账协议恢复，技术失败只在允许前态和期限内重试。

1. 获得锁后校验 execution\_mode=LIVE 且租户发布开关开启，job 未取消/过期、epoch 与 active\_pipeline\_revision 正确、帖子版本未变且未删、分身授权与可见性有效、输入人设及记忆版本有效、全部来源 guard 的 epoch/墓碑/权限仍有效，且审核适用于当前必需策略。

1. 按固定 key 顺序锁配额桶，分别检查当前动作的点赞或评论额度及预算预留；COMMENT 额度不足只拒绝该动作。每分身周期额度以 decision\_id 去重、避免组合动作重复扣整项额度；动作额度按 decision\_id+action\_type 扣减。锁与事务设置短超时，冲突时有限重试。

1. 按 action\_type 写唯一 interaction 并将该动作标记 SUCCEEDED，同事务写该动作的通知、索引、记忆 outbox。计划保持不变。两个动作均已就绪时可在一个事务提交；也可分别事务提交，已成功点赞不因评论失败而回滚。IGNORE 仅在冻结空计划时记录业务决定。

1. 提交后返回该动作结果和整项执行进度。响应丢失的重试返回同一动作已有结果，其配额与事件不重复产生；工作流继续推进原计划内尚未完成的其他动作。

需要修改 job 状态的事务按统一锁序获取前置 guard，首次获取 processing\_job 锁时直接使用写锁，避免共享锁升级；阶段提交只更新阶段/提案记录，任务聚合状态由独立条件更新事务维护。所有事务设置锁等待与执行上限，锁竞争重试仍受总业务期限约束。

事务示意（省略错误处理，不能直接用作生产 SQL）：

```sql
BEGIN;
-- 按固定顺序锁授权、目标及当前动作来源、job、decision、action 和配额。
-- 校验冻结计划包含 action_type，以及版本、epoch、期限与当前动作审核结果。
-- 若该动作已 SUCCEEDED，返回其回执，继续由工作流推进其他动作。
UPDATE action_execution
   SET status = 'SUCCEEDED'
 WHERE tenant_id = :tenant AND decision_id = :decision
   AND action_type = :action_type AND status = 'READY';
-- 检查受影响行数；仅胜出者写 interaction。
-- interaction 唯一键为 tenant_id + decision_id + action_type。
-- 原子消费该动作额度并写对应 outbox，随后汇总候选状态。
COMMIT;
```

关键唯一约束：decision\_slot(tenant\_id, post\_id, avatar\_id)、interaction(tenant\_id, decision\_id, action\_type)、consumer\_inbox(consumer\_name, event\_id)。动作类型进入互动唯一键，使点赞和评论各自幂等；尝试号、模型版本不进入唯一键。planned\_actions 一经冻结，重试不能改写集合或添加计划外动作。

### 9.2 删除、撤权与策略更新

所有内容编辑、删除、ACL、分身停用、屏蔽关系、记忆撤回及强制审核策略更新，都要通过同一 guard 协议推进 epoch。禁止某条后台脚本直接改权限明细而跳过 guard。不存在关系行时，固定 guard 仍能串行化新插入的屏蔽操作。

删除先提交时，发布必被拒。发布先提交时，随后的删除使帖子与互动在权威读取路径不可见。缓存仅提供正文或候选，展示前检查当前帖子及权限；离线通知允许有投递时差，通知打开时重新鉴权。已经被用户看到的内容无法撤回。

高热帖子同一 guard 的发布共享读取，额度桶更新才串行；有界评论数限制热点写入量。租户维度进行 home shard 路由，参与同一发布事务的目标及来源 guard、决策、权限 guard、互动及硬额度必须共址；正文和向量可以独立存储。跨租户来源不进入该事务域，只有经显式授权导入且有完整撤回契约的资料才能使用。关系或授权由外部服务独立拥有时，需引入能在发布服务生效的同步 epoch/fence 契约；最终一致的缓存不能满足严格撤权语义。

## 10. 外部发布、事件和通知

若点赞或评论由另一个服务拥有，本系统事务只能写 PUBLISH\_INTENT，不能称为互动已发布。下游必须提供稳定幂等键、最终回执查询、权威帖子版本与权限校验，以及需要时的撤回接口。每动作幂等键固定为 decision\_id+action\_type，不随网络重试变化；下游逐动作保存发布意图与回执。

下游收到命令后在自己的权威事务内校验和发布，返回持久 receipt；本地记录该动作 receipt 后才将该动作标记 SUCCEEDED/PUBLISHED 并产生对应事实记忆事件。LIKE 成功而 COMMENT 为 UNKNOWN 时，保留点赞、回执及“已点赞”记忆，整项保持部分完成并待对账；重试只恢复未决评论，不能重复点赞或提前记录“已评论”。发布超时优先查回执；无查询/幂等能力则 UNKNOWN 对账。持有本地数据库锁并调用 HTTP 不能获得跨服务原子性。

通知、搜索索引和记忆使用 outbox 至少一次投递。AWS Outbox 实践强调双写一致性及消费者去重，\[S6\] Kafka 对外部系统的效果也需要目标配合。\[S7\] 本方案不依赖 MQ 的投递语义替代业务去重。

消费者在目标存储支持事务时，将 inbox 去重和投影写入同事务；向量库和其他外部目标使用版本化幂等 upsert 与回执对账，不能先写 inbox 成功再执行外部副作用。通知入站记录与发送供应商也要区分，供应商缺少幂等时承认可能重复通知，不影响互动唯一性。

事件含 event\_id、schema\_version、tenant\_id、aggregate\_id/version、occurred\_at、trace\_id、payload\_ref。相同聚合的消息可按 key 路由，但所有消费者仍按版本拒绝过期更新。删除优先处理；失败进入可重放死信并保留原 event\_id。

## 11. 安全、隐私与数据生命周期

对原始媒体、prompt、私有记忆、模型输出分级授权和加密；日志与指标只保留必要 ID、错误码和统计。Temporal history、MQ payload、search attributes 仅传不含秘密的引用；授权读取引用时再次检查，不在 history 中存储长期签名 URL。

模型 Worker 无发布凭证，也不能任意访问其他分身记忆。公开与私有模型上下文使用不同的数据类型及构造器；CI 检查跨类型调用，红队用 canary 私密事实验证跨分身及公开输出泄露。

人设和记忆更新都记录版本。记忆更正/删除传播到索引、缓存、未提交提案和派生产物，保留最小必要墓碑。工作流所引用的对象保留至少覆盖任务最大期限与恢复窗口；法律或用户删除请求优先，相关任务取消并把引用失效作为确定结果处理。

上线前配置三类保留期：执行历史恢复期、业务幂等/回执期、内容与个人数据保留期。业务去重不能依赖已过期的 Temporal history；清理账本前必须证明没有可重放的旧事件或按产品规则关闭该身份的再执行入口。

## 12. 可观测性、SLO 与运维

以下为建议验收目标，不代表已有系统实测。正常运行与供应商故障分别统计，避免将外部异常从报表中隐藏。

| 维度 | 指标 | 初始验收方式 |
| --- | --- | --- |
| 正确性 | 重复互动、越权发布、旧版本发布 | 故障注入用例中均为 0 |
| 任务完整性 | 已接收 job 无账本、永久无结局 | 为 0；非终态均有 deadline/处置原因 |
| 延迟 | 受理、首个互动、整帖终态 P50/P95/P99 | 文本/图片/音视频分别建立容量基线 |
| 依赖 | 成功率、429、超时、UNKNOWN 年龄 | 分供应商、模型和错误类型告警 |
| 积压 | 最老任务年龄、outbox lag、索引版本水位 | 接近阶段预算即限流并告警 |
| 成本 | 每帖/有效评论 token 和费用、未决预留 | 预算硬上限与账单对账 |
| 质量 | 召回相关性、人设一致性、事实引用、重复评论 | 固定标注集和线上抽样 |

上线前由压测确定各内容类型的目标完成时限 D\_text、D\_image、D\_audio、D\_video，以及峰值 λ\_target；交付压测报告后冻结为 SLO 配置。发布门槛为在 λ\_target 持续负载和约定模型 mix 下，P95 完成时间满足对应 D，积压无持续增长。依赖故障期间的目标为不越权、不重复发布、预算有界、状态可解释，恢复后在约定 drain 窗口清空积压。

trace 关联 post\_id、job\_id、workflow\_id、stage\_key、operation\_key、decision\_id；高基数 ID 放 trace/log，不作为监控标签。日志不存私密正文。运营控制台提供任务进度、重试原因、UNKNOWN 对账、提案版本、审核证据和受控恢复入口。

模型限流时，降低准入和候选预算；审核故障时，暂停放行。索引延迟时，优先修复 outbox 和删除水位；工作流卡住时，先检查阶段与外部调用账本。批量重放前，先预估调用额度并限速，避免直接重置全部任务。

## 13. 故障恢复、升级与灾备

Worker 崩溃由 Temporal 重调度；成功阶段从业务账本复用，旧 epoch 返回被拒。数据库不可用时停止接收和提交，不向客户端报告持久化成功。MQ 不可用时 outbox 保留，达到积压阈值收紧准入；数据库正常的既有工作流可按依赖范围继续。

供应商故障隔离到对应模型队列，使用有限重试和网关熔断。Qdrant 不可用时等待或让任务明确失败，不能绕过匹配流程随机选分身。对象缺失分为暂时存储错误与已删除/已过期，后一类确定终止。

工作流发布优先固定 Worker 版本，新任务灰度切换，旧 Worker 保留到存量排空；已部署版本需核对对 Worker Versioning 的支持。变更控制流前执行历史 replay 测试，外部 Activity schema 同样保持兼容。工作流、模型、prompt 和策略不能只靠一个服务版本号隐式绑定。\[S8\]

主地域拥有写入权，灾备切换先 fence 旧写入者，再迁移数据库与编排访问，核对 PG job、Temporal 历史、outbox 和供应商回执。异步副本可能丢失已发布回执，恢复后必须对账；仅把备用地域 Worker 拉起无法保证无重复。RPO、RTO、恢复后幂等账本完整性与重放水位需进入演练报告。

模型决策 schema 示例：

```json
{
  "schema_version": "decision.v2",
  "planned_actions": ["LIKE", "COMMENT"],
  "reason_code": "SHARED_INTEREST",
  "confidence": 0.82
}
```

planned\_actions=\[\] 表示忽略，\[LIKE\]、\[COMMENT\] 和 \[LIKE, COMMENT\] 均合法；IGNORE 不作为可与其他动作并存的数组元素。模型选择与动作执行结果分开保存。公开生成输入由服务端另行构建，只包含 post\_public\_context、public\_persona、approved\_public\_facts 及固定风格约束。模型不能通过返回任意 avatar\_id、post\_id、tool\_call 或正文中的指令改写提交目标。

## 15. 测试与验收矩阵

### 15.1 正确性与故障注入

| 故障/竞争窗口 | 必须观察到的结果 |
| --- | --- |
| 帖子事务提交后、启动前 kill | outbox 重投，job 最终推进 |
| StartWorkflow 成功、确认前 kill | 固定身份恢复，业务流程不重复提交 |
| 模型成功、结果落库前 kill | 允许额外调用成本，最终一个冻结计划，每种动作最多一条互动 |
| 旧 Activity 超时，新执行接管后旧结果返回 | epoch/generation 拒绝旧写入 |
| 重试模型从 LIKE 改为 COMMENT，或返回重复动作 | 冻结计划保持不变；每种动作最多成功一次，未冻结时仅一个提案可胜出 |
| 评论生成中编辑、删帖、撤权、撤回记忆 | 旧提案提交失败或返回已提交原结果 |
| 发布与删除同时提交 | 满足第 9 节串行化及最终不可见语义 |
| 审核超时或媒体覆盖不足 | 自动互动为 0，状态保持待审或终止 |

特别增加提交窗口并发测试：旧发布事务读 epoch 后暂停，恢复器尝试升 epoch；恢复器必须等待事务结束或旧事务在恢复后因 epoch 不匹配失败。主流程汇总与 CANCELLED/SUPERSEDED 并发时，条件更新必须保留取消/替代终态。测试不能只覆盖两个操作完全串行的情况。

| 故障/数据问题 | 必须观察到的结果 |
| --- | --- |
| 外部发布超时且缺少查询能力 | UNKNOWN，自动盲重试为 0 |
| Qdrant 旧 upsert 晚于更新或删除 | 旧点被权威版本/墓碑过滤 |
| embedding 切换时旧查询仍在执行 | 请求固定 bundle，语义空间无混查 |
| 恶意帖子要求复述私密记忆 | 公开 prompt 无私密材料，canary 泄露为 0 |
| 重复投递互动事件 | 同类来源记忆只有一份 |
| 用户删除与日志/对象清理 | 检索立即失效，清理有可验证进度 |
| 跨历史保留期重放旧启动事件 | PG job 和决策账本拦截重复效果 |
| 数据库/Temporal 灾备数据进度不同 | 保持写入 fence，先对账再恢复发布 |

审查新增回归：同一 operation 连续两次 UNKNOWN 后替代调用，每个可计费 attempt 都独立占用预算；同 job 内记忆撤回后以新 generation 重算，旧结果迟到不能胜出；删除之后迟到的记忆事件无法新建来源已失效的记忆；一条记忆有多个 chunk 时点数和 manifest 一致；检索超时不能变成零候选 COMPLETED。

跨来源提交回归：读取源自 B 的记忆并生成 A 的评论，暂停在最终提交前，删除 B 但刻意暂停索引及 memory\_epoch 异步传播，随后提交 A 必须因来源 guard 失效而拒绝；反向调度验证提交先于删除的线性化语义。另用 A/B 相互引用的并发事务验证来源 guard 排序不会形成锁序反转。

### 15.2 负载与质量

负载模型覆盖文本/图片/音视频比例、媒体大小长尾、模型延迟长尾、候选分布和重试率。持续压测、突发压测、热点压测、依赖故障恢复分别执行；使用供应商模拟器验证系统机制，再在真实配额内校准模型性能。模拟器吞吐不能作为真实 AI 链路吞吐。

热点测试让单租户占 90% 输入，检查其他租户仍获得其配额和等待目标；90% 是测试分布，不是容量承诺。同时混入高 token 与低 token 请求，检查基于成本的公平份额，而非只比较请求数。持续 429、超时、MQ 暂停、索引暂停和长视频解码异常时，验证并发、预算、积压和恢复速率均有界。

效果评测使用固定标注集，覆盖同主题不同立场、冷启动分身、讽刺、跨语言、图文矛盾、视频时间轴、多模态审核遗漏和隐私诱导。评估 filtered Recall@K、候选相关性、动作合理性、人设一致性、评论事实支持率、重复度和单位有效互动成本。技术状态正确不等于语义判断正确，需独立设置质量发布门槛。

## 16. 实施批次与上线门槛

| 批次 | 交付内容 | 验收出口 |
| --- | --- | --- |
| 1 | 数据模型、幂等接收、工作流启动、状态查询、调用模拟器 | 重投、崩溃、恢复测试通过 |
| 2 | 多模态处理、审核、模型网关、预算与 UNKNOWN | 审核故障不放行，调用预算有界 |
| 3 | 公开召回、私有记忆、人设决策、评论审核 | 权限隔离、版本及效果集通过 |
| 4 | 最终发布、删除撤权、outbox 记忆与通知 | 并发正确性和回执对账通过 |
| 5 | 限流、公平性、压测、工作流升级与灾备演练 | 达到冻结的 SLO 和恢复目标 |

影子运行 execution\_mode=SHADOW，只向隔离的影子提案空间写结果，禁止占用正式决策槽、写互动或产生已互动记忆；影子模型调用仍计入单独费用预算。仅回放评测使用 REPLAY 模式，副作用入口同样拒绝。LIVE 发布接口在事务内检查执行模式和租户发布开关，避免依赖工作流分支约定来阻止误发。

灰度阶段使用明确租户/用户白名单、评论上限和费用上限。按影子、内部用户、小流量、逐步扩大推进。回滚通过第 9 节策略 guard 关闭发布开关并停止新准入，已提交内容保留；错误内容撤回走独立审计命令，避免回滚脚本误删正常互动。

上线前必须落实：互动权威库归属、所有 guard 写入方、模型供应商幂等/查询/保留能力、审核覆盖要求、SLO 与峰值目标、个人数据保留期，以及人工复核/UNKNOWN 对账责任人。本文给出默认业务语义和实现协议，这些环境参数需要在实施验收时补齐并逐项验证，基础设施就绪不能替代验证。

## 17. 交叉与对抗性审查记录

完整初稿由 3 个 agent 从工作流与事务、检索与容量、独立对抗审查三个视角阅读全文并交叉质疑。第一轮发现 6 项 P1 和 1 项公平性 P2；修订复核时继续发现 1 项跨来源提交 P1。全部修正后完成第二轮复核，当前发现的 P0/P1 均已闭合。审查属于设计推演，不能替代实现测试或证明系统不存在其他缺陷。

| 问题 | 对抗性反例 | 最终修正位置 |
| --- | --- | --- |
| P1：恢复 fence 缺少锁 | 读取旧 epoch 后恢复升代，旧事务仍提交 | 4.2、9.1：job 冲突锁及条件状态更新 |
| P1：费用预留不足 | UNKNOWN 后替代尝试再次收费，却复用一份预算 | 6、8.2：charge\_identity 独立预留 |
| P1：失效阶段结果复用 | 记忆撤回后同 job 重算，取到旧 SUCCEEDED | 4.1：generation 与输入快照绑定 |
| P1：多个 chunk 互相覆盖 | 同来源多段写入相同 point ID | 7.2：完整分块身份与 manifest |
| P1：迟到记忆复活 | 删除后旧互动事件创建全新派生记忆 | 7.3：来源 guard 与血缘读取校验 |
| P1：检索失败伪装成功 | 向量超时被汇总为正常零候选 | 5.1、8.2：失败、降级和零候选分离 |
| P1：跨来源撤回窗口 | A 引用 B，B 删除尚未传播时 A 发布 | 7.3、9.1：完整有界来源集合锁验 |
| P2：公平性缺少执行机制 | 热点租户不断抢占 retry\_after 后的额度 | 8.2：持久等待、成本加权 DRR |

复核还修整了 job 锁升级的表述，并要求实际 dispatch 前复验 permit 与速率窗口。主设计补充 LIVE/SHADOW/REPLAY 发布门禁和 active\_pipeline\_revision，使影子回放与旧策略均不能误发正式互动。上述问题均有第 15 节对应的验收场景。本次按业务要求修正动作语义：点赞与评论允许组合；独立审查补充了计划冻结与动作完成分离、评论失败保留合法点赞、逐动作幂等及回执、配额和血缘边界。组合回归用例包括两动作均成功、评论审核失败但点赞成功、点赞成功且评论 UNKNOWN 后恢复，以及两动作重复投递各仅成功一次。

最终复核结论：工作流与事务审查通过；检索与容量审查通过；独立对抗性审查通过。可以进入实现阶段，尚待完成真实数据库并发测试、供应商契约校准、模型质量/隐私评测、负载与灾备验证。剩余边界包括无幂等外部接口的 UNKNOWN、近似检索的漏召回、生成内容的语义风险以及灾备 RPO；这些边界已在相应章节规定处置方式。
